**(b) Create `docs/adr/0001-mcp-sampling-inversion-of-control.md`.**

Title line: `# 0001. MCP sampling is an inversion of control, not a tool`

`## Status` — `Accepted — 2026-09-22`.

`## Context` — **frame this as a build-or-don't decision, never as a defect report.** 10-RESEARCH.md
Pitfall 1 is explicit: a warning sign is an ADR opening with "agent86 fails to implement...". The
correct opening is that agent86 currently *declares* sampling unsupported, correctly, at the
protocol level. Cover:
- What sampling is on the wire: the server sends `sampling/createMessage`; the client answers via
  `sampling_callback`. Control inverts — agent86 stops being the thing that calls a model and becomes
  the model provider for a third party's request.
- Why agent86 does not do it today and why that is correct, with citations: `mcp_client.py:219`
  passes no `sampling_callback`, so `_build_capabilities()` (`session.py:591-595`) sets
  `sampling=None` and the capability is never advertised. A spec-compliant server will not even
  attempt the request. This is the protocol's own way of saying "not supported".
- The demand signal: cite the MCP-07 live-run section of `docs/mcp-conformance-audit-2026-09.md` by
  name, quoting what agent86 actually observed — including, if that is what happened, that
  `server-everything`'s `trigger-sampling-request` tools were absent from agent86's tool list
  *because* agent86 declared no sampling capability. Say what that means for demand: the only corpus
  server that drives sampling is the conformance instrument, not a realistic workload.
- The four things that make this expensive rather than merely new: (1) third-party spend inside our
  turn, charged against `limits.max_cost_usd`; (2) the completion becomes visible to the server, so
  it needs its own egress pass, not the one that covers model output to the user; (3) it needs its
  own approval gate — the existing per-tool gate does not cover a request the model never made;
  (4) whose model answers, at whose price, under which provider's key — and CLAUDE.md's hard rule
  that keys are never stored in config constrains any answer.

`## Decision` — first line begins `**Ruling:**`. Rule it. The evidence supports one of two defensible
rulings and you must pick exactly one and defend it:
- *opt-in per server, deferred until a realistic corpus server demands it* (the BACKLOG's own
  framing: "if it ships at all it is opt-in per server, and it needs an approval gate and an egress
  pass of its own"), or
- *written non-goal for now, recorded in `docs/ARCHITECTURE.md` §15*.
Whichever you pick, spell out the conditions that would reopen it, and sketch the shape it would
take if built: a per-server opt-in flag described as a future `MCPServerConfig` field in
`config.py`'s schema with write-back through `config_writer.py` (never TOML written from
`config.py`), a dedicated approval gate, an egress pass over the completion before it leaves, and
the sampled tokens folded into the same cost accounting sub-agents already use.

`## Consequences` — what stays true if the ruling holds (servers keep receiving a correct "not
supported"; no third-party spend path opens; MCP-16 stays deferred), what the ruling costs (any
server whose main value is sampling is unusable), and what the matrix row `CAP-SAMPLING` must say as
a result — state the in/out ruling explicitly here, because plan 10-04 copies it into the matrix.

**(a) Create `docs/adr/0003-mcp-schema-deferral-prompt-contract.md`.**

Title line: `# 0003. Schema deferral changes the prompt contract`

`## Status` — `Accepted — 2026-09-22`.

`## Context` — schema deferral means putting tool *names* plus server instructions in the system
prompt and fetching the full JSON Schema only on a tool's first use. That is attractive because MCP
tool schemas are the largest uncontrolled term in the fixed overhead. It collides with two
mechanisms that are real and present, not hypothetical — cite both:
1. **The budget term.** `conversation = window - (system prompt + tool schemas) -
   limits.context_reserve_tokens - max_output_tokens_for(...)` (`docs/ARCHITECTURE.md:615-619`).
   `tool schemas` is a *named, subtracted term*. Deferring schemas changes what that term means
   mid-session: today it is computed once per request from the full compiled set; in a deferred world
   it grows after each tool's first use. Note that `Harness._context_budget` already recomputes
   before every request (`docs/ARCHITECTURE.md:286-290`), precisely because skills, MCP servers and
   episodic recall change overhead mid-session — so the design structurally tolerates a growing term.
   Say that explicitly rather than leaving it implied.
2. **The `allowed-tools` gate.** "The compiled system prompt lists each skill's `allowed-tools`, so
   the boundary is known before a refusal costs a step" (`docs/ARCHITECTURE.md:543-544`). This is the
   distinction the ruling turns on: deferring *schemas* while still listing every tool *name*
   preserves the boundary and keeps a refusal free; deferring *which tools exist* destroys it and
   makes every refusal cost a step.

`## Decision` — first line begins `**Ruling:**`. The evidence points one way and the ADR should say
so plainly: deferral of schemas is permissible; deferral of tool *names* is not. State it as a rule
a future implementer can apply without re-reading this document, and add the second-order
requirements that follow from it — that the budget must be recomputed after a schema is materialised
(not only at turn start), that a deferred schema's first fetch is a synchronous cost inside the step
that needs it, and that `run --json` keys stay additive-only.

`## Consequences` — what MCP-20 (workstream C) inherits as a specification rather than an open
question; what breaks if a future implementer defers names as well; and what this implies for the
matrix (note: schema deferral is an agent86-side strategy, not a spec capability, so it gets no
matrix row — say so, so nobody goes looking for one).

**(b) Create `docs/adr/0004-mcp-result-cap-location.md`.**

Title line: `# 0004. Where the MCP result cap lives`

`## Status` — `Accepted — 2026-09-22`.

`## Context` — `_content_to_text` (`src/agent86/tools/mcp_client.py:426-434`) joins every content
part with no size limit anywhere in the function or at its call site (`call_tool`,
`mcp_client.py:292-293`), so a large resource dump goes straight into the context budget. The
contrast that gives this ADR its shape: a cap *does* exist on the observability side — the flight
recorder clips big free-text fields at `max_field_chars` (section 9) — but that is the trace, not the
prompt. Two facts widen the scope and must both appear:
- `CallToolResult.structured_content` is never read (`mcp_types/_types.py:1474`), so structured
  output is not merely uncapped, it is silently dropped.
- Non-text content blocks fall through to `str(chunk)` (`mcp_client.py:429-430`), so an image or
  audio block is already a Python repr in the prompt — capping bytes does not fix that, and the two
  should not be conflated.
State the candidate homes explicitly and weigh them: (i) a module-level constant in `mcp_client.py`;
(ii) a `[limits]` config key applying to every MCP server; (iii) a per-server `MCPServerConfig`
field — noting that `MCPConfig` carries only `enabled: bool` today (`src/agent86/config.py:293-294`),
so a per-server cap is a schema addition in `config.py` with write-back through `config_writer.py`,
never TOML written from `config.py`; (iv) the tool layer generally, capping every tool result rather
than only MCP's.

`## Decision` — first line begins `**Ruling:**`. Name the home. Say whether it is per-server and why.
Say what the cap does when exceeded — the ruling must specify the *behaviour*, not just the number:
truncate with an explicit marker the model can see and act on (the pattern the flight recorder
already uses), never silently drop, and never raise, because a tool must never raise into the loop
(CLAUDE.md). Give a default value and say where that number came from. State whether
`structured_content` is in scope of this ADR or explicitly out of it.

`## Consequences` — what MCP-22 (workstream C) inherits; the interaction with ADR 0003's budget term;
and whether any matrix row's ruling depends on this (`CAP-STRUCTURED-OUTPUT`, `CAP-CONTENT-BLOCKS`)
— state the answer, because plan 10-04 reads it.

Neither ADR may propose or make a code change in this phase.
