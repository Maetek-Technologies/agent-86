Plan-time corrections to 14-RESEARCH.md (verified by the planner with a scratch stdio server +
client against the installed `mcp` 2.0.0, 2026-09-24; Task 1 re-verifies and records them):
- **Progress is NOT sent unconditionally.** `ServerSession.report_progress` is documented "A
  no-op when the caller did not request progress" (`mcp/server/session.py:426-434`). A client
  that never passes `progress_callback` to `call_tool` never receives a single
  `notifications/progress`. With a `progress_callback`, the dispatcher both calls it AND tees the
  notification to `message_handler` (`mcp/shared/jsonrpc_dispatcher.py:659`, unconditional
  `_spawn(_contained_notify(on_notify), ...)`). Consequence for 14-04: `call_tool` passes a no-op
  `progress_callback` solely so the SDK mints a progress token; observation stays generic in
  `_on_message` (orchestrator ruling 3 — no per-call correlation).
- **`Context.notify_tools_changed()` does NOT reach agent86.** It publishes to the
  `subscriptions/listen` bus (`mcp/server/mcpserver/context.py:129-131`,
  `mcp/server/subscriptions.py` docstring: "2026-07-28, SEP-2575"), which a `2025-11-25`
  handshake client never opens. `ctx.request_context.session.send_tool_list_changed()`
  (`mcp/server/session.py:461-463`) DOES reach `message_handler` as a
  `ToolListChangedNotification`. The fixture must use the latter.
- **Logging arrives without `logging/setLevel`**: a server-side `ctx.log("info", ...)` reached the
  client's `message_handler` as a `LoggingMessageNotification` with no set-level request sent.
- `MCPServer(name, instructions="...")` → `InitializeResult.instructions == "..."` on the client.

def notify(self, manager: MCPManager, notification: Any) -> None:
    """Deliver ``notification`` (e.g. an ``mcp.types.ToolListChangedNotification()``) to the
    currently-installed ``message_handler`` on the manager's loop, and wait for the handler to
