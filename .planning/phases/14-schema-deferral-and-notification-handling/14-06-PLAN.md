- `CAP-LIST-CHANGED` → `implemented` / `in`. All three siblings routed; tools re-fetched via
  `list_tools()` only; resources/prompts siblings produce a live note and the same re-fetch;
  identity-preserving; race-guarded against death/stop.

  `tools/call` (no-op `progress_callback` so the SDK mints a token — a compliant server sends none
  otherwise, `14-EVIDENCE.md`), observed generically as a throttled live note plus
  `last_progress(server)`, **not attributed to a specific tool call**, not requested for
  resources/prompts/completion calls.
- `CAP-RESOURCE-SUBSCRIBE` → `implemented` / `in`: `notifications/resources/updated` now surfaces
  as a live note naming the URI and the `read_resource` tool — the half Phase 11 left to MCP-24.
- `CAP-LOGGING` → `partial` / `out`: `notifications/message` is routed to agent86's Python
  logger at the mapped level; `logging/setLevel` is never sent and log lines never reach the
  transcript; the capability is deprecated in `2026-07-28` (SEP-2577).
- `CAP-CANCELLATION` → stays `absent` / `out`: incoming `notifications/cancelled` is consumed by
  the SDK dispatcher before `message_handler` (`mcp/client/session.py:1435-1437`), so notification
  routing cannot close it; the unbuilt half is client→server cancel forwarding (Escape/Ctrl+C, a
  `call_timeout_s` overrun).
