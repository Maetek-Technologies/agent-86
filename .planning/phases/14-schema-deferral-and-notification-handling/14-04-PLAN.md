<objective>
MCP-24: the `_on_message` handler Phase 12 installed stops dropping server notifications.
`list_changed` (tools, and the resources/prompts siblings) re-fetches the server's tool list
through Phase 12's existing `_emit_tools_changed` → `Harness._on_mcp_tools_changed` plumbing
(no new registry-sync mechanism); progress, logging and resource-updated notifications reach
something other than a no-op.

Rulings (recorded for executor and verifier):
- **list_changed scope** (orchestrator ruling 4, research Open Question 4). All three siblings
  run the same re-fetch, which re-runs `session.list_tools()` ONLY — `_capability_tools()` is
  never re-run: server capabilities are fixed for a session's lifetime (spec), so the existing
  synthetic tool objects are reused as-is. Resources/prompts siblings therefore mutate the
  registry only if the server's own tool list really changed in the meantime; their visible
  effect is a live note (the synthetic `list_resources`/`list_prompts` tools already fetch live on
  every call). This satisfies SC3's literal "routes … into a re-fetch of that server's tool list"
  at the cost of one `tools/list` round trip.
- **Identity preservation.** A re-listed tool whose `(description, schema, read_only)` equals the
  existing `MCPTool._definition` (added by 14-03) keeps the SAME object — so it is neither
  removed-then-re-added in the registry nor re-deferred. A tool with the same name but a changed
  definition is replaced (old object removed, new object added).
- **Race guard (research Pitfall 2).** The re-fetch awaits `list_tools()` and then writes only if
  `self._sessions.get(name) is session` (the exact session the handler's `_serve_once` owns);
  otherwise it returns silently — the death/stop path already owns cleanup. Re-fetches for one
  server are serialized by `self._refetch_locks[name]` (an `asyncio.Lock`, created on the loop
  thread on first use).
- **Inline await is safe.** The handler runs on the MCP loop thread in a task the SDK spawned per
  notification (`mcp/shared/jsonrpc_dispatcher.py:659`, `_spawn(_contained_notify(on_notify), ...)`),
  so awaiting `session.list_tools()` inside it cannot deadlock the reader, and no
  `run_coroutine_threadsafe` is used (research anti-pattern).
- **Progress** (orchestrator ruling 3, corrected by 14-EVIDENCE.md fact 3). A spec-compliant
  server sends NO progress unless the request carries a progress token, so `call_tool` passes a
  module-level no-op `_request_progress` as `progress_callback` purely so the SDK mints one.
  Observation is generic in `_on_message` (the SDK tees every progress notification there): the
  latest `(progress, total, message)` per server is kept for `last_progress(server)`, and a
  live-only note (`_add_note(..., persistent=False)` — event log + listeners, never the
  startup-rendered `notes` list) fires at most once per `_PROGRESS_NOTE_INTERVAL_S = 2.0` per
  server, always on completion (`progress >= total`). Not attributed to a specific tool call —
  recorded as the CAP-PROGRESS scope in 14-06. `_on_session` (resources/prompts/completion
  calls) does NOT request progress.
- **Logging.** `LoggingMessageNotification` → `logger.log(level, "MCP server %r [%s]: %s", ...)`
  on `agent86.tools.mcp_client`'s logger, levels mapped from the eight RFC 5424 names; no note
  (transcript noise), no `logging/setLevel` request. CAP-LOGGING therefore becomes `partial`
  (receive-side routed), decided in 14-06.
- **Resource updates.** `ResourceUpdatedNotification` → live note
  `"MCP server '<name>': subscribed resource updated: <uri>; re-read it with mcp__<name>__read_resource."`
  — the half of `CAP-RESOURCE-SUBSCRIBE` that Phase 11 left to MCP-24.
- **Cancellation.** Nothing. `CancelledNotification` never reaches `message_handler`
  (`mcp/client/session.py:1435-1437`); client-side cancel forwarding is a separate unbuilt
  feature. 14-06 records this in the matrix instead of claiming the row.
- Server-supplied text in any note is whitespace-flattened and clipped to
  `_NOTIFICATION_TEXT_MAX = 200` characters.
</objective>

```python
    async def _refetch_tools(self, name: str, session: Any, reason: str) -> None:
        """Re-list one server's tools after a list_changed notification (MCP-24). Never raises.

        Re-runs ``list_tools()`` only: capabilities are fixed for a session, so the synthetic
        capability tools are reused. An unchanged tool keeps its object (and its ADR 0003
        materialised flag). Writes only while ``session`` is still this server's live session,
        so a notification racing stop_server()/a death can never resurrect it (Pitfall 2).
        """
        lock = self._refetch_locks.setdefault(name, asyncio.Lock())
        async with lock:
            try:
                listed = await session.list_tools()
                fresh = list(listed.tools)
            except Exception as exc:  # noqa: BLE001
                if self._sessions.get(name) is session:
                    self._add_note(f"MCP server '{name}': re-listing tools after {reason} failed: {_describe(exc)}")
                return
            if self._sessions.get(name) is not session:
                return
            old = self._server_tools.get(name, [])
            old_remote = {t._tool: t for t in old if isinstance(t, MCPTool)}
            capability = [t for t in old if not isinstance(t, MCPTool)]
            remote: list[Tool] = []
            for t in fresh:
                definition = (t.description or "", _tool_schema(t) or {"type": "object", "properties": {}}, _is_read_only(t))
                prev = old_remote.get(t.name)
                if prev is not None and prev._definition == definition:
                    remote.append(prev)
                else:
                    remote.append(MCPTool(self, name, t.name, t.description or "", _tool_schema(t), read_only=_is_read_only(t)))
            kept = {id(t) for t in remote}
            removed: list[Tool] = [t for t in old_remote.values() if id(t) not in kept]
            previous = {id(t) for t in old_remote.values()}
            added: list[Tool] = [t for t in remote if id(t) not in previous]
            self._server_tools[name] = remote + capability
            if removed or added:
                self._add_note(
                    f"MCP server '{name}' changed its tool list ({reason}): added "
                    f"{', '.join(t.name for t in added) or 'none'}; removed "
                    f"{', '.join(t.name for t in removed) or 'none'}."
                )
                self._emit_tools_changed(name, removed, added)
```
